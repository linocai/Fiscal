## 1. 顺序、事实与共同边界

严格串行：`F4-A → F4-B → F4-C`。每块都必须是 Builder → Independent Review → 同一 Builder 修复/复测 → Independent Review；**终审 0 findings** 才解锁下一块。不得以截图、模型测试、SnapshotTool 或旧 P34 QA 代替真实 iOS/macOS UI runtime。F4 全部终审前，F5、正式 `*RootView.swift`、旧 View 删除和发布仍锁定。

- **已存在的服务端事实**：P34 已终审，月报 `GET /reports/monthly/{YYYY-MM}`、年报 `GET /reports/yearly/{YYYY}`、同 revision 下钻和 PDF/CSV 均为服务端生成；公开年份严格 `0002–9998`，时区 `Asia/Shanghai`、币种 `CNY`。P31 已提供 merchant 关系和 Archive additive tables；Archive 是加密同步传输，真实 restore 只允许空目标库。
- **已存在但尚未可直接用的 V15 seam**：`V15ReportsService` 已有 month/year/read/export 入口，但月份/年份本地未限制 `0002–9998`，drill-down item 仍为 raw `JSONValue`、`dimension/source/account_kind` 未作 forward-compatible typed read，筛选参数未暴露；artifact 由调用方假定 revision，transport 不读响应元数据或真实传输进度。必须先修成 schema-shaped Foundation，再做任何 Feature。
- **不可变呈现规则**：服务端是金额、排序、口径、状态和 revision 的唯一来源。禁止客户端汇总、扣除、同比/环比、预测或“本月表现”文案；不做预算、建议、评分、预测、银行连接器、离线写队列或 Web/new library。`personal_realized` 是支出主口径；`personal_expected`、expected/received reimbursement 等只显示服务端字段，不在客户端相减造新指标。
- **全块横向规则**：CNY `Int64` minor units；业务期/文件名以 Shanghai；未知 additive enum/object 只读显示、不可筛选/执行；request 的 period/filter/revision/cursor 始终同属一个 immutable read owner。任何 load、filter、period、lens、dismiss、retry、refresh 或 offline 状态变化都递增 generation；取消和旧页不得写回新 owner。分页失败保留已读页；409 接管整个报告/导出决定面，重新 GET（忽略 cache）后才可再下钻/导出。
- **离线**：允许只读加密 snapshot，并明确保存时间；没有 snapshot 显示失败而非空报告。PDF/CSV/Archive export、恢复预检和所有密码输入均 offline disabled + 原因，绝不排队或把旧 artifact 当新报告。
- **视觉与结构**：继续用原生 SwiftUI、既有 `V15/DesignSystem` 和 `Shared` 状态表面，code/state first；设计启动资料只作视觉/交互意图，不复制 HTML。iOS 报表为全屏决定面；macOS 报表和系统与数据均为单窗口接管（明确“返回脊柱”，不新开窗口），接管态自带右侧上下文，不依赖正式 root。

所有 F4 代码只可落在 `App/Sources/FiscalKit/V15/{Foundation,Features/Reports,Features/DataSecurity,Shared}`、并行 Gallery/AppShell、对应 tests/QA；Feature 不得 import 旧 `Data/`、旧 DTO、旧 `Features/Reporting*`、`FiscalDesign`、root 或 raw transport/`JSONValue`。fixture/gallery 位于既冻结的 `V15/Shared`，不是生产 Feature 的旁路。源码清单变动后运行 `cd App && xcodegen generate`；仅处理生成的 scheme 噪声，绝不 reset/revert 用户目录迁移。

## 2. 服务端契约、缺口与开工裁定

### 2.1 F4-A 的既有 P34 read contract（可直接接入）

| 目的 | 精确 GET 契约 | 成功事实 | 失败/缓存规则 |
| --- | --- | --- | --- |
| 月报 | `/api/v1/reports/monthly/{YYYY-MM}` | `PeriodReport{meta{period_kind,period,date_from,date_to,timezone="Asia/Shanghai",currency="CNY",as_of,data_revision,report_schema_version,generated_at},summary,accounts,categories,merchants,sources,completeness,drill_down_path}` | `0000/0001/9999` 或坏月：422 `invalid_report_month`；read 中 revision 改变：409 `period_report_changed`，有本报告 reload path。 |
| 年报 | `/api/v1/reports/yearly/{YYYY}` | 同一 `PeriodReport`，年期间 | 超界/坏年：422 `invalid_report_year`；同一 409 规则。 |
| 明细 | `/api/v1/reports/period-drill-down?period_kind=month|year&period={YYYY-MM|YYYY}&expected_data_revision={report.meta.data_revision}&category_id?&account_id?&merchant_id?&source?&cursor?&limit=1..100` | `PeriodReportDrillDownPage{meta,dimension="ledger",category_id,account_id,merchant_id,source,items[{transaction_id,occurred_at,business_date,kind,source,category_id/name,merchant_id/name,external_cash_amount_minor,gross_consumption_minor,merchant_refund_minor,net_consumption_minor}],next_cursor}` | filter/revision-bound opaque cursor；篡改或跨 filter：422 `invalid_period_report_cursor`；旧 revision：409 `period_report_changed`，只能重载相同 period 的首屏。省略全部 filter 的语义是全 period，**不是**任一 aggregate row 的下钻。 |

`summary` 的 16 个字段均须 decode/display-ready：`income/gross_consumption/merchant_refund/net_consumption/expected_reimbursement/received_reimbursement/personal_expected/personal_realized/net_income_expense/cash_inflow/cash_outflow/cash_net/internal_transfer_inflow/internal_transfer_outflow/credit_debt_at_period_end/reimbursement_outstanding_at_period_end`（全部 `_minor`）。类别、商户、账户、来源和完整性行是服务端 row，不能裁成 Top N 或重排后假称完整分布。内部转账只作为单列流入/流出，绝不进入外部 cash net。

F4-A Foundation 必须把上述行变为 typed DTO：report period 初始化即拒绝 0001/9999；known `TransactionKind`、`TransactionSource`、`AccountKind`、`ReportPeriodKind` 和 `dimension` 有 `.unknown(String)` / display-only 分支，未知值不导致全屏 decode 失败，也不生成 query/action。`V15PeriodReportDrillDown.items` 不得继续暴露 raw JSON。读服务显式接受各 filter、`cursor`、`limit=1...100` 与 cache policy；所有 filters 只能由当前 report row 的稳定 ID / known source 构造。

**行级 drill 能力是显式 typed 状态，不是“省略 filter”回退**：只有 `category_id != nil` 的分类行、`merchant_id != nil` 的商户行、稳定 `account_id` 的账户行，或 known `source` 的来源行，可以以该唯一 filter 加同一 `expected_data_revision` 打开 drill。`category_id == nil`、`merchant_id == nil`、所有 completeness 行及 unknown source 都是 display-only：控件保留 disabled，稳定原因是“此汇总没有可安全定位的明细筛选条件”，并且 **0 次** `/period-drill-down` 请求。不得把空 ID、名称、`nil` 或空 filter 传到 route 后把全 period ledger 伪称成该行明细；若以后需要 null/unclassified/completeness drill，必须先有另审的 Backend additive filter/identity contract。

### 2.2 F4-B 先行后端子块（硬依赖，不得由客户端假定）

当前四个 export path 都从新的 `PeriodReport` 直接生成 bytes，带 `Content-Disposition`、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`，但**没有**要求与屏幕所见 `data_revision` 一致；现有 `V15ReportArtifact(dataRevision:)` 只是调用方注入，不能证明 artifact 所属 revision。F4-B Builder 的第一步是 Backend ownership（schema/route/service/tests）完成下列 additive 兼容扩展并独立审查，之后才可改 Apple export UI：

| path | 新 query（V15 必传；为旧客户端保留 optional） | success headers | stale |
| --- | --- | --- | --- |
| `/reports/monthly/{period}/export.csv|pdf` | `expected_data_revision?: int >= 0` | 保持 attachment、正确 content type、`Cache-Control: no-store`、`X-Content-Type-Options: nosniff`；新增 `X-Fiscal-Data-Revision: {canonical report.meta.data_revision}` | provided revision 不同或 read-boundary 改变：409 `period_report_changed`，details 含 expected/current revision 与精确 monthly reload path。 |
| `/reports/yearly/{period}/export.csv|pdf` | 同上 | 同上 | 同上，精确 yearly reload path。 |

服务端必须先构造一份 canonical report、比较 expected revision，再从**同一对象**产生 CSV/PDF/header/filename；不允许 JSON、CSV、PDF 之间重新读库。保留 P34 的 UTF-8 BOM+CRLF+formula guard、PDF 全部分页、5 MiB 上界、安全字段集合和 legacy `/transactions/export.csv` 区分。P34 新增测试必须证明四个 endpoint 的 optional legacy compatibility、V15 same-revision success、写入 race 409、header/filename/revision 一致、401、cache/no-store/nosniff、公式 title/note、完整账户标识、credential、Provider 原文都不在 report export。

Foundation 随后把 artifact transport 扩成带 method/body/`Accept`、`Content-Disposition`、content-type、confirmed server revision 的 typed response；收到非预期 type/header/revision 即 fail closed，不落盘/不 share。当前 `URLSession.data(for:)` 只能提供真实 indeterminate transfer，5 MiB hard limit 内不伪造百分比或逐字节回调；Feature 不得自建 URLSession/raw request。

### 2.3 F4-C Archive/DataSecurity 裁定（真实能力，不伪造恢复）

当前唯一正常 API 是认证 `POST /api/v1/archives/export`，JSON body `{password: 12...128 chars, include_ai_raw: false}`，返回 `application/vnd.fiscal.archive+json` attachment `fiscal-archive-v1.far`，并有 `no-store/nosniff`。ArchiveService 采用 scrypt + AES-256-GCM；export 排除 access credential/key、Provider secret，默认替换 AI raw input；真正 `open → dry_run_report → restore_empty_target` 只存在 operator CLI，并且 restore 必须 schema-version 相同、关系预检通过、**空目标**和 canonical seed，不能对当前 live database merge/overwrite。

因此 F4-C 的先行 Backend/contract audit 结论固定如下：

1. Apple 端只能请求 `include_ai_raw=false`，不出现“含 AI 原文”开关；报告 PDF/CSV 永远不含凭证、完整账户标识、transaction title/note、账单/Provider 原文。Archive recovery artifact 本身仅按已验证的 encrypted relationship payload 处理，页面/fixture/日志/错误/文件名不得泄露其内容、密码、access key、Provider 值或完整账户标识。
2. 现有 API 没有安全的 live restore destination，也没有 manifest/restore history/job/progress endpoint。F4-C **不得**新增“恢复到当前库”、伪百分比、伪 receipt 或虚假恢复历史；下载前的“正在创建加密归档”只能是不确定服务端阶段，response 开始后的百分比只能来自真实传输字节。
3. F4-C 的真实 restore 验收继续走 `fiscal_api.cli.archive --dry-run`、然后隔离 fresh target `--apply --confirm-empty-target`；必须逐项验证 manifest/entity count、FK relationships、data revision、posting/account financial fingerprint，并保留 source 与 target 的 P34 report 同额证据。若产品后来要求在 App 内选择 archive 并恢复，**停止 F4-C 并另立 Backend restore-destination/authorization contract**；在没有用户批准的目标、备份与管理员授权前，不得设计 destructive REST restore。

这不是可绕过的缺口：F4-C UI 仅呈现“已导出 / transfer failed / result unknown”和恢复前置条件，真实 restore 由上述受控 Operator workflow 证明。它不改变 archive/history 的服务器事实，也不把静态 fixture 当恢复成功。
