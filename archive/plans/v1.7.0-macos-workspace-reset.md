# Fiscal v1.7.0 · macOS 工作台重整执行记录

> 状态：PLANNED ｜建议版本：v1.7.0（Build 34）｜基线：v1.6.0（Build 33）

本记录展开 [PROJECT_PLAN.md](../../PROJECT_PLAN.md) 的 B17-A～B17-D。用户最新指令优先于旧原型、旧计划和旧视觉审查：保留当前配色与基础风格，删除余额核对，重做 macOS 信息架构；不自动发布。

## 1. 要交付的产品结果

1. macOS 左侧变为五个固定一级入口：`流水`、`未来现金流`、`报表`、`系统与数据`、`设置`。
2. “流水”继续是中央账目列表 + 右侧详情。月份和账户放在流水标题栏；账户余额始终可见，不依赖侧栏滚动。
3. 月流水只显示所选月的真实账目。未来账单、工资、报销、信用到期和计划现金流全部离开这里，进入“未来现金流”。
4. “记一笔”放到工作区右上，搜索保留在同一条工具栏；删除密度切换和无意义顶栏元素。
5. 余额核对从产品、客户端、服务端和数据库消失。用户输入实际余额只换来“有差额”的旧链路不再存在。
6. 报表 v2 的内容和计算不重做，只去掉核对统计并提升入口。其余正常账务能力保留。

## 2. 不做什么

- 不重画品牌、配色、字体、圆角或基础控件语言；不做一套新皮肤。
- 不改变 iOS 的首页结构、报表职责、现金流职责或截图快捷指令。iOS 仅清除被删除功能的入口与代码。
- 不删除账目、posting、账户、信用账期、分期、报销、现金流、导入或归档数据。
- 不把“需要决定”换个名字搬回来，也不新增泛化待办中心。
- 不发布 v1.7.0，除非用户另行明确授权完整发布。

## 3. 导航与页面合同

| 模块 | 用户看到什么 | 现有能力怎样安放 |
| --- | --- | --- |
| 流水 | 月份、账户余额/选择、搜索、记一笔、中央真实流水、右侧详情 | `V15LedgerModel`、分类、批量分类、账户详情继续使用；未分类是账目自身状态，不再是一块左栏筛选。 |
| 未来现金流 | 当前现金流摘要、已知未来事项、信用到期、报销待回款、计划条目 | 复用 `V15CashFlow*`、`V15FutureTimeline*` 与既有安全对象导航；只显示已录入/已排期事实。 |
| 报表 | 原有消费、现金流、债务和 drill/export | 直接使用 `V15ReportingMacView`；删除“对账差异”这一行。 |
| 系统与数据 | 账单导入、归档、AI 待确认及其他低频维护 | 保留现有页面和数据；不再用主流水筛选伪装这些入口。 |
| 设置 | 账户/分类和本机设置 | 账户可从流水上下文栏选择并进入详情；管理操作仍在设置。 |

“待同步”是离线写入的安全状态，不是导航模块：有待同步内容时在相关工作区给出小而直接的状态与处理入口。真实的导入失败、信用逾期、报销逾期和现金流逾期由各自模块呈现，不能再堆进总表。

## 4. B17-A：余额核对删除的准确边界

### 后端

- 移除 `api/routes/reconciliation.py`、`services/reconciliation.py`、`repositories/reconciliation.py`、`db/models/reconciliation.py` 中的核对模型及 `api/p21_schemas.py`；从 `api/router.py`、`api/dependencies.py`、模型导出和 data-revision scope 中解除引用。
- `reconciliation/attention` 目前还混有未分类、导入、信用、报销、现金流和 AI 的通用事项。新版本不保留这个总表；这些事项必须回到各自模块。确认每种既有 source 都还有直达、可理解的地方后，删除总表 API、`AttentionDismissal` 和它的静音记录，不能悄悄吞掉真实问题。
- 从 `services/reporting.py`、`repositories/reporting.py`、`api/p7_schemas.py`、`api/p34_schemas.py`、`services/report_exports.py` 删除“最近核对、对账差异、核对 completeness issue”和相应导出字段。
- 从 `services/credit.py`、`repositories/credit.py` 及信用账期契约中删除 checkpoint 对改期/保留旧账期的特殊限制和 `preserved_checkpoint_count`；保留改期本身所有 ledger、分期、AI、导入保护。
- 同步清理 accounts/transactions/credit routes 中过时的 `reconciliation`、`attention` mutation scope，以及 archive/恢复完整性检查和所有只测核对的测试夹具。

### 数据迁移与保护

1. 新建**唯一线性** migration `0038_remove_reconciliation`，只以 production head `0037` 为前置。
2. 上生产前停止写入，创建并验证新的宁波 PostgreSQL 备份；只记录核对表的行数和按 target kind 的计数/摘要，不把实际余额和备注散落到日志或文档。
3. migration 在确认没有代码引用后删除 `reconciliation_checkpoints`；`attention_dismissals` 只有在所有通用提醒已被移除且确认没有其他使用者时删除。它们的历史只由已验证备份保留，不复制进新的产品表。
4. migration 不提供“重建已删余额核对数据”的 downgrade。若要回退，按项目规则停写、备份当前库、把验证过的迁移前备份恢复到新目标并完成校验；绝不盲降 Alembic。
5. 先在一份含账户、信用账期、核对记录、导入和 archive 引用的 PostgreSQL fixture 上跑 `0037 → 0038`；确认账本和其他业务表逐条保持，只有批准删除的两类表/静音偏好消失。

### 已安装旧客户端的兼容

- v1.6.0 的 Swift `Codable` 把 `reports/facts` 和 period report 的核对字段当必填。新 v1.7.0 客户端会完全删除这些字段。
- 后端在**一个明确、短期的过渡版本**里可对旧的两条报表读取返回 `0/null` 占位，使老客户端仍能打开正常账本；占位不读取表、不计算、不显示、不能操作。
- `/reconciliation/*` 不保留假功能：路由移除。旧客户端若主动打开已删除的“核对”只会得到不可用，不能写入或误导。
- 用户确认 macOS 和 iOS 都已升级到 v1.7.0 后，下一次小改动删除这两个不可见占位字段。这个临时兼容层不是永久债务，也不延迟删除数据库数据。

## 5. B17-B：macOS 实施范围

主要所有权是 `App/Sources/FiscalKit/V15/AppShell/V151MacWorkspace.swift`；不要另起一套根壳。

1. 删除 `V151MacLedgerLens`、`Density`、左栏筛选/月份/账户滚动区、`futureRows` 和泛化 attention rows。保留当前紧凑行高，作为固定值。
2. 将左栏替换成短小的模块导航，选中态沿用现有 teal/中性配色。不会出现第二个 TabView、第二条隐藏导航或第四个永久窗格。
3. 为“流水”做紧凑上下文栏：月份选择、全部账户/单账户选择和可见余额、搜索、右上“记一笔”。窄窗口时账户条可横向滚动或折叠为清晰菜单，但不移回左栏。
4. 月份切换固定走 `Asia/Shanghai`。它清空旧选择、派生报表和分页；账户切换同样清空不再属于该账户的选择。两者各自只影响自己的范围，旧请求不能覆盖新界面。
5. 账目列表继续默认“全部正式流水”。账户详情仍在右侧，删除“进入余额核对”及所有核对历史；账目详情、批量分类、作废/恢复和现有 preview/commit 规则不降级。
6. 未来现金流入口复用现有 `V15CashFlowMacView`、`V15FutureTimelineMacView` 和已验证的对象归属检查；对象失效时显示原因，不猜测跳转或写入。
7. 现有低频 destination 不能丢失：导入、归档、AI 待确认落到“系统与数据”；信用、报销、分期的未来相关操作落到“未来现金流”中的明确入口或其已有详情页。

## 6. B17-C：共享 Swift 与 iOS 最小收口

- 删除 `V15ReconciliationContracts.swift`、`V15ReconciliationModel.swift`、`Features/Reconciliation/`、`Data/ReconciliationRepository.swift`、旧 Domain/Feature reconciliation 模型、`V15Services.reconciliation`、深链 checkpoint 读取及 fixtures。
- `V15TodayReadModel` 不再并行读取 `/reconciliation/attention`；删除注意事项总表状态和深链分支。保留 facts、scope、账户/账目安全读取、离线和 generation 守卫。
- `V15Contracts.swift`、报表 model/view 与 fixtures 删除核对字段，所有空态与导出断言相应更新。
- `V151IOSWorkspace` 和 iOS credit/account sheet 只删除“核对”目的地、菜单、入口、标签和提醒分支。其余 iOS 页面布局不改；需要在没有核对 API 的情况下冷启动、切换页面、查看报表和操作账目。

## 7. 验收

- Ruff、Pyright、完整 PostgreSQL suite；新增 `0037 → 0038` populated-upgrade 测试。
- 核对 route、OpenAPI 项、表、模型、报告字段、导出表头和运行时查询全部消失；任何剩余引用均为失败。
- 信用账期改期、archive/restore、账户删除保护、正常 reports v2、known future、现金流、导入和 preview/commit 回归通过。
- 将 migration 前后的表清单、备份校验和 production record 写入未来 `archive/releases/v1.7.0/RELEASE_STATE.md`，不提前伪造发布证据。

### Apple

- `FiscalKitTests` 全量通过；构建 `FiscaliOS` generic simulator 与 `FiscalmacOS` target。
- macOS Gallery/RootSmoke 覆盖：五个模块均可达；左栏无旧筛选；账户不用滚动即可见；月份和账户不串状态；中央流水不含未来；右侧详情和“记一笔”可达；报表/未来现金流入口可达；无核对文案或按钮。
- 手工视觉检查 macOS 常用宽度与 1000pt、浅色/深色、长账户名/金额、空态、加载和错误态；沿用现有色彩与密度，不评判为“新设计”。
- iOS 在 iPhone 13 普通字号、AX5、浅深色验证：没有核对入口或请求，其他根导航、账目、报表、现金流和既有截图快捷指令无回归。

## 8. 风险与施工顺序

- 最大风险不是删页面，而是 checkpoint 同时被报表、信用改期和通用提醒引用；B17-A 必须先做全局引用清单和 migration fixture，任何残留都阻止 DDL。
- 第二风险是过早删掉 report 必填字段让已装 Build 33 不能读正常数据；采用上文有限、无状态的占位兼容，不保留核对功能。
- 第三风险是为重排 macOS 而意外重做 iOS；代码审查以“iOS diff 只能是核对删除与共享契约修正”为门。
- 实施顺序：B17-A 后端契约/迁移与测试 → B17-B macOS 壳 → B17-C 共享/iOS 收口 → B17-D 全量验证与视觉验收。只有用户明确授权后才进入发布链。
