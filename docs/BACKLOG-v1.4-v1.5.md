## 1. 长期产品定位

Fiscal 是一套单人、私用、仅 CNY 的个人财务事实系统。它负责：

1. 诚实记录已经发生的财务事实。
2. 接收并整理用户明确提供的未来财务事项。
3. 核对账本与现实账户、账单之间是否一致。
4. 清楚展现过去、现在和已经知道的未来。
5. 让所有数字都能追溯到正式流水、账户、账期、账单、报销、现金流事项或用户输入。

Fiscal 不负责替用户制定预算、评价消费、建议如何花钱，或预测用户尚未提供的未来行为。

### 1.1 不可越过的边界

- 不做预算、预算额度、预算执行率或“超支”评价。
- 不做“安全可花多少”、消费建议、节流建议或财务健康评分。
- 不做情景模拟、消费决策辅助、退休规划或投资建议。
- 不做银行账号密码托管、网银爬虫或自动银行连接器。
- 不做 AI 财务聊天，不让 LLM 自由查询并解释全部个人财务。
- 不做多人、家庭共享、投资组合或多币种。
- 不因为导入、AI、缓存或报表方便而建立第二套金额真相。
- 不允许 AI 或导入器直接写 posting、改余额或自动生成平账流水。

### 1.2 贯穿 v1.4–v1.5 的共同原则

- **统一账本是唯一金额真相。** 所有正式写入继续经过现有领域服务、校验、幂等和 revision 契约。
- **AI 只负责识别，不负责决定。** LLM 输出永远是待审核候选，不是正式流水。
- **PDF 导入永远人工确认。** 不受现有 AI 自动执行开关、金额阈值或质量策略放宽影响；不得存在“以后自动确认此类账单”。
- **实际、确认、预计、计划、推导必须分开。** UI、API、导出和报表不得把不同确定性混为一个数字。
- **程序负责校验，LLM 不负责证明。** 金额合计、余额等式、重复检测、日期边界和 posting 规则由确定性代码完成。
- **服务端拥有报表口径。** Apple 客户端只展示服务端返回的金额和口径说明，不自行拼接关键财务指标。
- **默认最小化敏感数据。** 原始 PDF、完整卡号、姓名、地址、客户号和 Provider 请求内容不得进入日志、Git、截图夹具或 QA 文档。
- **所有新数据都纳入 P22/P23。** 新实体必须覆盖 Archive、恢复、data revision、离线标识、AI 质量事件和生产恢复验证。

## 3. v1.4 · PDF 智能账单导入

### 3.1 版本目标

让用户从 macOS 或 iOS 选择一份银行/信用卡 PDF，由 Fiscal 将其转换为可审核的交易候选。用户能看到每一行候选来自 PDF 的哪一页、原文是什么、系统做了什么判断、是否与已有流水重复、账单是否对平。只有用户明确确认的行才进入正式账本。

### 3.2 v1.4 完成后的主流程

```text
选择 PDF
  → 展示隐私与 Provider 说明
  → 计算文件指纹、识别页面类型
  → PDFKit 提取文本 / Vision 本地 OCR
  → 必要时经单次授权发送文本或指定页面图像给 LLM
  → 严格 JSON Schema 结构化
  → 确定性金额、日期、余额和合计校验
  → 匹配账户、账期和已有流水
  → 用户逐行修正或批量处理
  → 最终确认页列出将创建、匹配、忽略的行
  → 用户明确确认
  → 正式领域服务原子写入
  → 生成导入结果和 P21 核对入口
```

### 3.3 首发支持范围

v1.4 首发只承诺：

- CNY 个人银行账户流水 PDF。
- CNY 信用卡账单 PDF。
- 有文本层的 PDF。
- 扫描型或图片型 PDF，经 Apple Vision 本地 OCR。
- 单账户账单；一个文件内识别到多个账户时必须拆分或阻止确认。
- 支出、收入、转账候选、信用消费、还款、退款和费用候选。
- 账单期初/期末余额、借贷合计、账单应还额等字段“存在则校验，不存在不伪造”。

首发不承诺覆盖全部银行版式。初期以用户实际使用的 2–3 类账单建立合成/脱敏契约夹具，再逐步扩展解析器 profile。

### 3.4 P24 · 导入与隐私基础

#### 目标

先建立不接触正式账本的导入批次、来源证据、生命周期、隐私授权和 Archive 契约。

#### Backlog

- [ ] 冻结 `StatementImport`、`StatementImportPage`、`StatementImportRow`、`StatementImportAttempt`、`StatementImportResolution` 的领域边界。
- [ ] 为导入批次建立状态机：
  - `created`：已登记文件指纹，尚未解析。
  - `extracting`：客户端正在提取文本/OCR。
  - `parsing`：Provider 正在结构化。
  - `review_required`：存在未处理候选或校验问题。
  - `ready_to_confirm`：所有选中行满足正式写入要求。
  - `partially_confirmed`：部分行已原子确认，其余行仍待处理。
  - `confirmed`：全部行已被创建、匹配或明确忽略。
  - `failed`：当前解析尝试失败，批次及历史尝试仍保留。
  - `abandoned`：用户放弃；不得自动恢复或继续写入。
- [ ] 文件唯一性使用 SHA-256、字节数、页数和 MIME 共同记录；原始文件名仅作显示，不参与唯一性。
- [ ] 同一文件指纹重复导入时先展示旧批次，不直接创建第二套候选。
- [ ] 定义原始 PDF 的保留策略并在编码前锁定：
  - 推荐默认：服务端不长期保存原 PDF。
  - 解析阶段只使用临时字节，任务结束即删除。
  - 服务端保存文件指纹、页号、证据原文/裁剪坐标、解析结果和用户修正历史。
  - 若未来需要保存原件，必须作为独立、显式、加密的附件能力另行立项，不能顺手加入 v1.4。
- [ ] 定义跨设备限制：原 PDF 不在当前设备时，仍可查看已保存证据文本和候选，但不能伪装成完整原件预览。
- [ ] 每次发送 LLM 前展示：Provider、模型、将发送文本还是图像、页数、字段脱敏结果和本次用途。
- [ ] 用户必须对每个导入批次单独授权 Provider 调用；设置页总开关只能允许能力，不能代替本次授权。
- [ ] 默认遮盖完整卡号/账号、姓名、地址、客户号、身份证号，仅在匹配所必需时保留机构名和尾号。
- [ ] Provider 请求、响应和异常日志禁止记录完整账单文本；只记录 batch ID、attempt ID、模型版本、耗时、token 数、状态和稳定错误码。
- [ ] 新增 `statement_imports` data revision scope；批次编辑只刷新导入界面，不刷新账本报表。
- [ ] 扩展 Fiscal Archive：包括批次、候选、证据、解析版本、分辨结果和正式流水链接；默认不包括原 PDF。
- [ ] Archive 恢复后，已确认导入与正式流水的来源链接必须完整；未完成批次可以继续审核或明确放弃。

#### 建议核心字段

`StatementImport` 至少包含：

- `id`
- `document_sha256`
- `byte_size`
- `page_count`
- `mime_type`
- `display_name`
- `institution_name_raw`
- `account_hint_masked`
- `statement_period_start/end`
- `currency`
- `status`
- `latest_attempt_id`
- `version`
- `created_at/updated_at/confirmed_at/abandoned_at`

`StatementImportRow` 至少包含：

- 稳定行 ID 和批次内顺序。
- 页号、证据原文、可选 bounding box。
- 原始交易日、入账日、原始摘要、原始金额字符串和借贷方向。
- 结构化金额 minor units、交易类型候选、账户/分类/账期候选。
- Provider 原始候选快照和用户最终值。
- 字段级 diff、校验警告、重复候选和当前 resolution。
- 已创建或已匹配的正式 transaction ID。
- 行版本、确认时间和确认操作 ID。

#### P24 验收

- [ ] 创建、失败、重试、放弃导入批次不会改变 ledger、posting、账户余额或报表。
- [ ] 相同文件重试不会产生重复批次或重复解析行。
- [ ] 日志、QA 证据、错误响应不泄露账单正文和身份字段。
- [ ] Archive 往返后批次、行、证据、状态和正式链接一致。
- [ ] 旧客户端忽略新增 scope 后仍可使用 v1.3 全部功能。

### 3.5 P25 · PDF 本地提取与 OCR

#### 目标

在 Apple 设备端可靠判断 PDF 类型，尽可能本地获取结构化前的页面证据，减少向 Provider 发送的信息。

#### Backlog

- [ ] 使用 PDFKit 读取页数、页面尺寸、文本层和页面文本。
- [ ] 对每页分类：`text`、`scanned_image`、`mixed`、`unsupported`。
- [ ] 文本型页面保留阅读顺序、行块、表格区域和页号，不只保留一个无位置信息的大字符串。
- [ ] 扫描型页面使用 Vision 在设备端 OCR；支持中英文数字、货币符号和常见日期格式。
- [ ] OCR 输出保留行级 bounding box，供 macOS 原文定位和用户复核。
- [ ] 混合页面合并文本层与 OCR 时按区域去重，禁止同一行被两种来源重复识别。
- [ ] 检测重复表头、跨页续表、页脚、免责声明和“上一页结转/下一页续”行。
- [ ] 大文件设置明确上限：文件大小、页数、单页像素、OCR 总字符数；超过上限在 Provider 调用前阻止并解释。
- [ ] PDF 密码保护、损坏、空白页、旋转页、双栏和异常页面尺寸都有稳定错误或降级状态。
- [ ] 在设备端计算文件哈希；任何重试继续使用同一批次和同一文档身份。
- [ ] 提取结果经过规范化但不改写金额、负号、日期或小数点；原文证据另存，不被清洗结果覆盖。
- [ ] 提供“发送前预览”，允许用户查看实际将发送给 LLM 的文本或页面范围。
- [ ] 图像多模态只在纯文本/OCR不足时出现，并要求本批次再次确认指定页面。

#### 测试夹具

- [ ] 文本型单页储蓄卡流水。
- [ ] 多页信用卡账单，跨页重复表头。
- [ ] 扫描型账单。
- [ ] 中英文混排、全角符号和千分位金额。
- [ ] 退款、负数、括号负数和借/贷两列。
- [ ] 同日多笔相同金额。
- [ ] 旋转页面、双栏、表格换行、金额与商户跨行。
- [ ] 损坏、加密、空白和超限文件。
- [ ] PDF 正文含“忽略系统指令”等提示注入文本；必须始终作为不可信账单内容处理。

#### P25 验收

- [ ] 全部合成夹具可重复得到同样的页数、行顺序和证据定位。
- [ ] 文本/OCR/混合模式不会静默丢页或重复行。
- [ ] 未授权时没有任何账单内容离开设备。
- [ ] 临时 PDF 和页面图像在任务结束、失败和取消后均按策略清理。

### 3.6 P26 · LLM 结构化与质量留痕

#### 目标

让 LLM 将不统一的银行版式转换为严格候选结构，同时完整保留原始判断、修正和失败证据。

#### P26-A · 冻结的最小 Provider 契约

本切片只将已经持久化的、确定性脱敏的 P24-B/P25-B evidence package 发送给 Provider，并保存可审计的结构化解析结果；它不是记账、匹配、确认或 P28 工作台。它独立于 P23 的 `AIProvider`/`AIProposal` 自动执行通道，不能继承其设置、阈值或写账能力。

**授权与启动**

- 唯一入口为 `POST /api/v1/statement-imports/{id}/provider-attempts`，要求 UUID `Idempotency-Key`、batch `expected_version`、当前 `evidence_sha256` 和 `authorization.confirmed=true`。
- `authorization` 必须绑定本次用户已查看的 Provider 标识/模型、prompt/schema version、页号集合、行数、redaction version/计数和 evidence hash；服务端逐项与当前 batch、已保存 evidence 及安全 Provider 配置比对。客户端只确认，不上传文本、页面、文件或自定义 prompt/model/URL。
- 授权只能启动一个新的 `provider_parse` attempt，先持久化授权快照并把 batch 转为 `parsing`，再在数据库事务/锁外调用 Provider。每一次 retry 都需要新的 `Idempotency-Key` 和新的本批次明确授权；同 key+同 payload 重放返回同一 attempt/终态，异 payload 冲突且绝不再次外呼。
- 预览由 Apple 的 `StatementImportEvidencePreview` 直接渲染脱敏 package，并在发送按钮上列出 Provider、模型、页数、行数、redaction count 与“只发送文本/坐标、不会发送 PDF 或图像”。没有这次显式确认或 offline snapshot 时，不得调用入口。

**Provider 请求允许面**

- 服务端从已保存 evidence 构造请求，**只**发送：`schema_version`、`currency="CNY"`、每页 `page_number/source_kind/evidence_text_masked`，以及每行 `row_number/page_number/evidence_text_masked/bounding_box(x,y,width,height)`。坐标为 `[0,1]` 的归一化位置，只用于行证据关联；允许页号/页型，不发送页面尺寸、旋转、像素或 OCR 原始来源。
- 明确禁止：PDF bytes、文件/图片 URL、页面图像、原始/规范化前文本、display name、document/import/attempt ID、document hash、byte size、机构/账户原始提示、完整账号/卡号、姓名、地址、客户号、身份证/电话/邮箱、Provider 凭证和任何日志/错误正文。Provider 不能获得工具、网页访问或执行能力。
- 脱敏只依赖版本化的确定性代码，而不依赖 LLM：先遮盖带标签的身份字段及连续/分隔的账号卡号，再遮盖电话、邮箱、身份证等确定性模式；服务端对将外发的每个字符串独立复检。无法确定为安全的值拒绝发送并以稳定本地错误结束 attempt，不能降级为发送原文。`[REDACTED]` 不是可推断字段。

**严格输出与快照**

- Provider 只可返回 `statement-provider-v1` 的 JSON Schema（`additionalProperties=false`、无 Markdown/自由文本/工具调用）。顶层为 `document` 摘要和 `candidates`；候选至少含唯一 `source_row_numbers`、可空的交易/入账日期（`YYYY-MM-DD`）、原始 CNY decimal string、方向、受限交易类型、摘要证据、`uncertain_fields` 与无法解析 source refs。日期仅是 Asia/Shanghai 业务日，不伪造时刻；金额由服务端一次性以 Decimal→`Int64` minor units 校验，禁止 float。
- 每个非空候选值必须能由其 source rows 的已脱敏文本确定性证明；不确定则返回 `null`/`uncertain_fields`。输出不得包含账户、分类、账期、正式 transaction ID 或不在 evidence 中的对手方/余额。服务端拒绝未知枚举、额外字段、越界数量、非 CNY、无 source ref、不可证明文本、无效日期/金额及超大响应。
- 每个 provider attempt 追加不可变的 `authorization`、redacted request 和**已通过 schema 的** initial result snapshot（含 Provider/model/prompt/schema/evidence hash、耗时和 token 计数）。无效上游 body 不保存；只留稳定错误码。快照及其 source refs 是 P26 的当前候选读模型，P27 才把用户最终值/resolution 物化到正式导入行；P26 不创建 transaction、posting 或 ledger candidate。
- Archive 必须包含 attempt 与这些仅脱敏快照、实体计数、hash 和 source-ref 关系；默认排除 PDF/image、未验证上游 body、Provider key/URL 和所有原始证据。恢复后可只读查看或重试，不能把旧授权自动复用。

**失败、revision 与最小验收**

- 取消、timeout、429、5xx、网络故障、无效 schema 或服务端验证失败都使当前 attempt 终态为 `failed`，batch 回到 `failed` 可重试；不留下半套 candidates、不会改 pages/rows evidence、更不会写 ledger/posting。429/5xx/timeout/网络统一为稳定的不可用错误，不暴露上游正文；取消保留独立稳定错误码。配置/授权/evidence preflight 未通过时零外呼、零 attempt、零 revision。
- 授权启动和每个已提交终态各自最多增加一次 `data_revision`，affected scope 永远仅 `statement_imports`；idempotency replay、只读预览和 preflight 拒绝不增加 revision。不得复用全局 AI 自动执行、策略或 quality-event 作为 PDF 确认机制。
- P26-A 自动门**只**使用注入、无网络的 synthetic adapter；不得调用真实 Provider、读取 Provider 配置/密钥或要求用户授权真实外发。它断言外发 envelope 没有禁传字段且提示注入仅作为数据；覆盖严格 schema/证据证明/金额边界失败、授权/idempotency/retry、取消/429/5xx/timeout 零半套结果、Archive 往返快照/source refs，以及每条路径 ledger/posting=0 与 revision scope 精确。完成后在 `docs/qa/p26/results.md` 记录命令、精确 revision 和已知全量回归边界。

#### Backlog

- [ ] 为账单识别建立独立 target/source，不复用单笔 `AIProposal` 的自动执行路径。
- [ ] Provider 只能返回严格 JSON Schema；禁止 Markdown、自由文本解释和工具调用。
- [ ] 顶层结构至少包含：
  - 机构和账户提示。
  - 账单期间、期初/期末余额或本期应还等摘要字段。
  - 逐行交易候选。
  - Provider 明确标记的不确定字段和无法解析片段。
- [ ] 每行金额先保留原始 decimal string，再由服务端统一转换为 CNY minor units；拒绝二进制浮点。
- [ ] LLM 不得生成账单证据中不存在的账户、分类、交易对手、日期或余额。
- [ ] LLM 自报 confidence 只能作为提示，不能作为自动确认依据；最终 `needs_review` 由确定性缺失项、校验失败和匹配冲突决定。
- [ ] 保存不可覆盖的首次 parse snapshot、Provider/model/prompt/schema 版本和字段级用户修正 diff。
- [ ] 每次 retry 创建新 attempt，不覆盖旧结果；用户可以比较两次解析，但只能选择一个作为当前候选基线。
- [ ] 将 PDF 识别纳入 P23 质量闭环，统计：
  - 文档解析成功率。
  - 行识别完成率。
  - 金额/日期/方向/摘要字段修改率。
  - 确定性校验通过率。
  - 重复匹配准确率。
  - 用户忽略率和整批放弃率。
- [ ] 质量异常只能使解析更保守、要求更多人工检查或关闭某个 profile；不能开启自动确认。
- [ ] 账单正文中的提示注入、URL、二维码文字和伪 JSON 全部作为数据，不得改变系统指令或触发网络/工具操作。

#### P26 验收

- [ ] 同一 parse attempt 的原始输出不可被后续编辑覆盖。
- [ ] 错误 JSON、额外字段、超大金额、非 CNY、无时区日期和非法枚举在进入候选前失败。
- [ ] Provider 超时、429、5xx 或取消不会产生半套交易候选，更不会写账。
- [ ] 真实 Provider 未调用时，可用 synthetic provider 完整验证解析、修正、放弃和重试链。
- [ ] 不存在任何配置可以让 PDF 行自动进入正式账本。

### 3.7 P27 · 校验、去重、匹配与正式确认

#### 目标

在 LLM 识别之后，用确定性领域逻辑证明候选是否内部一致，并让用户决定每一行是新建、匹配还是忽略。

#### 3.7.1 账单级校验

- [ ] 若账单提供期初/期末余额，验证：期初 + 流入 − 流出 = 期末。
- [ ] 若账单提供借方/贷方合计，验证明细合计。
- [ ] 若信用卡账单提供本期应还、上期余额、还款、退款、费用等摘要，按该 profile 明确公式校验。
- [ ] 若提供逐行余额，验证相邻行余额变化。
- [ ] 验证交易日期和入账日期是否落在合理账单窗口；窗口外项目允许存在，但必须标记。
- [ ] 检测页缺失、行序中断、重复表头被当成交易、金额列错位和摘要/金额跨行错配。
- [ ] 所有校验结果标记为 `passed`、`failed` 或 `unavailable`；缺少摘要不能伪装成通过。
- [ ] `failed` 批次仍可查看和修改，但最终确认页必须显著说明未对平项。

#### 3.7.2 重复与已有流水匹配

- [ ] 文件级强重复：相同 document SHA-256。
- [ ] 行级强匹配：银行稳定流水号或同一批次稳定 external reference。
- [ ] 行级候选匹配：账户、方向、金额、交易/入账日期窗口、规范化摘要和来源关系组合。
- [ ] 同日同金额只能生成候选，不能自动认定重复。
- [ ] 多个已有流水同时匹配时必须人工选择。
- [ ] 已确认的历史导入行再次出现时，展示原批次和正式流水链接。
- [ ] 匹配已有流水只建立来源链接，不静默改标题、分类、账户、日期或金额。
- [ ] 若用户决定修改已有流水，必须跳转普通流水编辑流程，经过原有 optimistic version 和业务校验。

#### 3.7.3 行分辨方式

每行最终必须是以下之一：

- `create_new`：以用户最终确认字段创建正式流水。
- `match_existing`：链接至一个已有正式流水，不新增 posting。
- `ignore_non_transaction`：用户确认其为表头、摘要、利息说明等非交易内容。
- `ignore_intentional`：确认为交易但用户选择不导入；保留原因和证据。
- `unresolved`：尚未决定，阻止批次完成。

#### 3.7.4 正式交易语义

- [ ] 储蓄卡/现金账户支出、收入继续走普通 `expense` / `income`。
- [ ] 账户之间的移动必须明确目标账户后走 `transfer`；只看到单边记录时不得凭空猜目标账户。
- [ ] 信用卡消费走 `credit_purchase`，并由服务端分配账期。
- [ ] 信用卡还款必须明确支付账户、信用账户和目标账期；若 PDF 无支付账户，只能匹配已有流水或等待用户补齐。
- [ ] 退款沿用现有退款/报销领域口径，不用负支出偷代语义。
- [ ] 银行费用、利息等必须有明确分类后才可创建。
- [ ] 任何差额不得自动生成 `balance_adjustment`；只能引导至 P21 诊断和普通正式修正流程。
- [ ] 新增正式来源 `statement_import` 及稳定 import/row provenance；公开 API 不允许普通调用者伪造该来源。

#### 3.7.5 确认事务

- [ ] 最终确认请求必须携带 batch expected version 和 UUID `Idempotency-Key`。
- [ ] 一次确认操作内选中的所有 `create_new` 行原子成功或全部失败。
- [ ] `match_existing` 和 ignore resolution 与本次确认在同一事务中落地。
- [ ] 重放相同 idempotency key 返回原结果；不同 payload 重用同 key 必须冲突。
- [ ] 确认前再次检查账户/分类/账期版本和归档状态，防止长时间审核后的陈旧引用。
- [ ] 每次确认只增加一次全局 data revision，scope 至少覆盖 `statement_imports/ledger/accounts/credit/reconciliation/attention/reports` 中实际受影响项。
- [ ] 确认结果返回每行 resolution、transaction ID、版本和受影响 scope。

#### P27 验收

- [ ] 同一文件、同一行和同一确认请求均无法重复记账。
- [ ] 批量中任一行失败时不存在部分 posting。
- [ ] 导入创建的每种交易与手工创建得到相同 posting、余额、信用账期、报表和撤销行为。
- [ ] 匹配已有流水不会改变账本金额。
- [ ] 未对平账单可以保存为待处理，但不能被 UI 误报为“验证通过”。
- [ ] 导入后可从正式流水追溯到批次、页号和证据，也可从批次跳转正式流水。

## 4. v1.5 · 事实展现升级

### 4.1 版本目标

把 Fiscal 已有信息整理成三个清晰方向：

- **过去**：我实际花了什么、收到什么、钱去了哪里。
- **现在**：我目前有多少现金、多少信用负债、多少待回报销，账本与现实最近何时核对。
- **已知未来**：已经明确或由现有领域事实推导出的未来支付和回款。

v1.5 不预测用户之后可能消费什么，也不评价任何消费是否合理。

### 4.2 统一术语

| 术语 | 含义 | 是否进入“扣除已确认应付后余额” |
| --- | --- | --- |
| 已发生 | 已进入正式账本的真实交易 | 已反映在当前现金余额，不重复计算 |
| 准确应付 | 信用账期等由正式账本和领域规则确定的到期金额 | 是，若到期日在所选窗口内 |
| 已确认计划 | 用户明确确认的未来现金流支出 | 是，若日期在所选窗口内 |
| 预计计划 | 用户记录但尚未确认的未来事项 | 否，单独展示 |
| 计划分期 | 已建立分期计划、但尚未成为准确账期应付的期次 | 否，单独展示为计划负债 |
| 预计回款 | 报销或用户计划的未来流入 | 否，不默认拿未到账收入抵扣应付 |
| 未知未来消费 | 用户未录入、系统仅能从历史猜测的消费 | 不计算、不展示、不预测 |

### 4.3 P30 · 事实口径与统一未来事项投影

#### 目标

先消除同一信用应还同时出现在 forecast、cash flow 和 credit due events 中造成的重复风险，再建立全部客户端共用的事实快照契约。

#### Backlog

- [ ] 审计当前 Overview、Cash Flow、Debt、Credit、Installment、Reimbursement 的未来金额来源和重复路径。
- [ ] 建立服务端 `KnownFutureEvent` 派生 read model，不新建第二套状态机。
- [ ] 每个事件必须有稳定 `source_type/source_id`、日期、方向、金额、certainty、标题和深链目标。
- [ ] certainty 固定为：
  - `exact_due`：账本和领域规则确定的到期额。
  - `confirmed`：用户明确确认的未来事项。
  - `expected`：用户或报销流程提供的预计事项。
  - `scheduled`：分期等已有计划但尚非准确到期额的事项。
- [ ] 统一去重规则：信用账期作为一个事实源，只能在聚合中计一次；不同 UI 可以引用同一事件，不能重新计算金额。
- [ ] 内部现金账户转账不改变总现金余额，不进入总额扣减；可在账户级时间轴分别展示流出/流入。
- [ ] 已到账/已支付事件在业务日切换后退出未来投影，并由正式流水接替。
- [ ] 编辑、撤销、还款、退款、报销到账和账期重排后，未来事件与 data revision 同事务收敛。
- [ ] 所有聚合使用 checked Int64、CNY minor units 和 Asia/Shanghai 业务日期。
- [ ] 响应保留 `as_of`、窗口起止、数据 revision 和口径版本。

#### 建议的事实快照字段

- `current_cash_balance_minor`
- `current_credit_debt_minor`
- `reimbursement_outstanding_minor`
- `confirmed_due_outflow_minor`
- `expected_outflow_minor`
- `scheduled_outflow_minor`
- `confirmed_inflow_minor`
- `expected_inflow_minor`
- `after_confirmed_outflow_minor`
- `unresolved_import_count`
- `uncategorized_transaction_count`
- `open_reconciliation_difference_count`
- `last_reconciled_at`
- `known_future_events`

其中唯一新的组合金额定义为：

```text
扣除已确认应付后余额
= 当前现金余额
- 所选窗口内的准确应付
- 所选窗口内的已确认未来支出
```

明确排除：预计支出、计划分期、预计回款、未知未来消费和现金账户内部转账。

#### P30 验收

- [ ] 同一信用账期无论被多少界面引用，聚合只计算一次。
- [ ] “扣除已确认应付后余额”可由响应中的组成项精确复算。
- [ ] 预计回款不会掩盖即将发生的已确认支出。
- [ ] 负数正常显示，不附加“危险”“不可消费”等评价。
- [ ] 所有金额都能深链到组成事件或正式领域对象。

#### P31 验收

- [ ] 修改商户归一不会改变 transaction amount、posting、账户余额或历史原始摘要。
- [ ] 分类、商户、账户、来源等不同切片的合计与同一消费口径守恒。
- [ ] 退款链接前后消费净额遵循既有报表契约，不重复扣减。
- [ ] 同比/环比在月份长度、闰年和时区边界下正确。

### 4.5 P32 · 当前财务快照与数据完整性

#### 目标

让总览准确回答“我现在还有什么”，同时明确数据是否已经核对、是否仍有未确认资料。

#### 建议总览主指标

- 当前现金余额：现金与储蓄卡正式余额。
- 当前信用负债：尚未结清的信用债务。
- 待回报销：尚未实际到账的报销本金。
- 扣除已确认应付后余额：采用 P30 固定公式和默认 30 天窗口。

#### Backlog

- [ ] 主指标统一从事实快照接口读取，不由 iOS/macOS 各自拼接。
- [ ] 每个指标显示 `as_of`，离线时显示快照时间和离线标识。
- [ ] 现金余额可下钻账户构成和各账户最近核对时间。
- [ ] 信用负债可下钻账户、账期、已还、剩余和到期日。
- [ ] 待回报销可下钻报销单、参与方、已收和未收。
- [ ] “扣除已确认应付后余额”旁提供公式说明和所选窗口，不使用“可花”“安全”“剩余额度”等措辞。
- [ ] 完整性区域只报告事实：
  - 未归类流水数量/金额。
  - 待确认 PDF 批次和行数。
  - 未对平账单。
  - 存在差额的 reconciliation checkpoint。
  - 各账户最近核对日期。
- [ ] Attention Center 继续承载需要处理的事实，不在首页复制全部状态机。
- [ ] 首页保持克制；更多分类、商户和趋势进入报表，不继续堆叠卡片。
- [ ] macOS 保持密集工作台，iOS 保持列表优先和单一底栏。

#### P32 验收

- [ ] 首页四个金额与账户、账期、报销和未来事件下钻完全一致。
- [ ] 离线快照不会显示“实时更新”，恢复联网后按 P22 revision 收敛。
- [ ] 没有数据完整性问题时不占用大面积提醒；存在问题时能深链到处理入口。
- [ ] 不出现预算、评分、建议或推测性措辞。

### 4.6 P33 · 已知未来时间轴与扣除应付后余额

#### 目标

把未来 7/30/60/90 天已经知道的支出和流入按确定性分层展示，让用户自己理解并作决定。

#### Backlog

- [ ] 提供 7、30、60、90 天窗口；默认 30 天。
- [ ] 时间轴按日期排序，同日按 exact due、confirmed、expected、scheduled 稳定排序。
- [ ] 每行明确显示来源标签：信用账期、用户确认现金流、预计现金流、分期计划、报销回款等。
- [ ] 支出与流入分列汇总，不默认用预计流入抵扣已确认支出。
- [ ] 顶部展示：当前现金余额、准确/已确认应付、扣除已确认应付后余额。
- [ ] 预计支出、计划分期、已确认流入和预计流入在下方分别陈列。
- [ ] 无日期的待回款单列，不塞入任意日期或窗口。
- [ ] 分期计划在尚未形成准确账期应付前标记 `scheduled`，不得伪装成 exact due。
- [ ] 某个未来事项入账后，时间轴通过正式流水和 revision 更新，不保留重复幽灵条目。
- [ ] 用户可以从事件进入账期、分期、报销或现金流详情；不能在时间轴直接绕过领域流程改金额。
- [ ] 允许按账户过滤；总现金视图排除内部转账净影响，账户视图保留单边变化。
- [ ] 提供口径说明页，列出每类事件是否进入顶部组合金额。

#### P33 验收

- [ ] 7/30/60/90 天窗口边界在 Asia/Shanghai 日期切换和月底正确。
- [ ] 同一未来事实不重复出现或重复计入。
- [ ] 还款、报销到账、现金流 settle、退款和分期变更后时间轴立即收敛。
- [ ] 预计和计划事件永远不会被 UI 视觉上伪装为已经确定。
- [ ] “扣除已确认应付后余额”只做算术陈述，不产生任何消费建议。

### 4.7 P34 · 月报、年报与事实导出

#### 目标

把过去一段时间内已经发生和期末仍存在的事实整理成可保存、可复核的报告。

#### 月报内容

- 月初与月末现金余额及账户构成。
- 本月真实收入、原始消费、退款、报销预计/实际个人承担。
- 本月现金流入、流出和净额。
- 月末信用负债、下个窗口准确应付。
- 月末待回报销。
- 分类、商户和账户排行及完整下钻。
- 本月新增/确认的 PDF 导入批次及来源覆盖。
- 未归类、未确认导入和 reconciliation 差额等完整性事实。

#### 年报内容

- 12 个月收入、消费、现金流和期末余额序列。
- 年度分类、商户、账户、来源分布。
- 信用负债和报销待回的月末变化。
- 一次性支出与普通消费分开展示，但总额守恒。
- 年初/年末数据完整性和核对状态。

#### Backlog

- [ ] 所有报告由服务端版本化口径生成，客户端负责原生展示。
- [ ] 报告响应记录 period、timezone、currency、as_of、data revision 和 report schema version。
- [ ] 支持 PDF 和 CSV 导出；PDF 用于阅读，CSV 用于逐行复核。
- [ ] PDF 导出不嵌入原始银行 PDF、账单全文、完整卡号或 Provider 原文。
- [ ] 导出前显示包含范围和敏感字段说明。
- [ ] 报告中的每个聚合能回到明细查询；导出中保留稳定但非敏感的关联 ID。
- [ ] 历史报告默认按当前账本重算，并明确 `generated_at`；若未来保存快照，必须另立不可变 snapshot 契约。
- [ ] 月报/年报只陈述变化，不生成“本月表现”“财务健康”“建议削减”等文本。

#### P34 验收

- [ ] 报告各聚合与同期间正式流水/报表完全守恒。
- [ ] PDF、CSV 和屏幕展示使用同一服务端口径。
- [ ] Archive 恢复后相同 revision 生成相同金额结果。
- [ ] 导出文件不包含 Provider 凭证、访问密钥、完整账户标识和默认排除的 AI 原文。

### 4.8 P35 · 原生只读入口、生产验收与 v1.5 收口

#### 原生只读入口

- [ ] iOS 主屏/锁屏小组件候选：当前现金余额、下次准确应付、30 天已确认应付、扣除已确认应付后余额、待确认导入数量。
- [ ] 小组件默认隐藏敏感金额，是否显示由用户逐组件选择。
- [ ] 小组件只读；点击后深链至对应事实详情或处理入口。
- [ ] 小组件数据使用 P22 加密只读快照，必须显示更新时间，不得伪装实时。
- [ ] Spotlight 可搜索流水、商户、报销单和导入批次；搜索结果只显示必要摘要。
- [ ] App Shortcuts 可打开导入、核对、现金流和报表，但不新增任何无需确认的写入捷径。

小组件和 Spotlight 为 v1.5 的 P1 交付；如果影响核心事实口径与发布质量，可以延后到 v1.5.x，但不能牺牲 P30–P34 的正确性。

#### v1.5 发布门

- [ ] 过去/现在/已知未来三套口径均有自动契约测试和真实数据下钻验证。
- [ ] 当前现金、信用负债、待回报销、已确认应付和组合余额均能追溯到唯一事实源。
- [ ] 信用账期、现金流、分期和报销在未来聚合中不存在双算。
- [ ] 所有界面通过文案审查：无预算、建议、评分、安全可花或历史预测。
- [ ] 月报/年报屏幕、PDF、CSV 与正式账本守恒。
- [ ] 离线、跨设备写入和 archive 恢复后按 data revision 收敛。
- [ ] macOS 与 Kurisu 完成总览、过去报表、未来时间轴、月报导出和深链验收。
- [ ] 完成生产备份、影子恢复、迁移往返、全量金额对账和签名包验证后才发布 v1.5。

## 5. 跨版本工程契约

### 5.1 API 与兼容

- 新字段优先追加，旧客户端可忽略；改变既有口径时必须新增明确版本或新端点。
- 所有 mutable resource 使用 optimistic version。
- 所有正式批量写入使用 UUID idempotency key。
- 稳定错误继续使用统一 `{ error: { code, message, request_id, details } }`。
- 账单、商户、未来事件和报告都使用稳定 ID，客户端不得以标题或显示名建立关系。
- API 响应金额继续使用整数 minor units；外部 decimal string 只在边界解析一次。

### 5.2 数据库与恢复

- 每个 migration 必须通过 upgrade、downgrade、re-upgrade 和 fresh PostgreSQL 全量测试。
- 生产 migration 前必须生成并验证备份；head 不同不做盲目应用 rollback。
- 新表和链接必须纳入 Archive、实体计数、哈希和恢复关系校验。
- 导入确认、商户关系变化和未来事实变更必须正确产生 data revision 和受影响 scope。
- 删除/放弃导入批次不得级联删除已经确认的正式流水或 provenance。

### 5.3 安全与隐私

- PDF 和账单文本始终视为不可信外部输入。
- LLM 调用禁止工具、网页访问和任意代码执行；只允许严格结构化输出。
- 账单正文中的提示、链接和二维码内容不能影响系统指令。
- Provider API key 继续只保存在服务端安全配置，不进入 Apple 客户端。
- 不在日志中记录账单正文、商户明细、完整金额列表或身份字段。
- 测试和截图使用合成/脱敏账单，仓库永远不提交真实银行 PDF。
- 本地临时文件、OCR 图像和请求缓存必须有取消/失败/完成三条清理路径。

### 5.4 性能与可观测性

- PDF 提取、OCR、文件哈希和大表格解析不得阻塞主线程。
- 导入任务记录页数、行数、阶段耗时、Provider 状态和失败码，不记录正文。
- 大批次列表分页或虚拟化；API 对行数和 payload 大小设置明确上限。
- 报表聚合需要真实规模性能基线；不能靠客户端缓存掩盖错误或陈旧数据。
- Provider 故障、解析失败、导入确认失败和 revision 不收敛进入 operations/attention 的事实告警。

## 6. 风险登记

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 银行 PDF 版式差异极大 | 漏行、错列、金额方向错误 | profile + LLM + 确定性校验；失败关闭确认，不假装通用支持 |
| LLM 幻觉 | 生成不存在的交易或字段 | 行级证据、严格 schema、禁止直接写账、逐批人工确认 |
| PDF 提示注入 | 污染 Provider 行为 | 文档视为数据、无工具、固定系统指令、严格输出验证 |
| 敏感信息外发 | 隐私泄露 | 本地优先提取、字段遮盖、逐批授权、发送前预览、最小化日志 |
| 重复导入 | 重复 posting 和余额错误 | 文档 hash、行 provenance、候选匹配、幂等确认、数据库唯一约束 |
| 信用卡语义错误 | 账期、还款、负债失真 | 明确 credit_purchase/repayment 领域路径；缺支付账户时阻止创建 |
| 账单未对平仍被确认 | 数据缺失难以发现 | 三态校验、显著差额、最终确认警示、P21 继续核对、禁止自动 adjustment |
| 未来金额双算 | “扣除应付后余额”错误 | P30 单一 KnownFutureEvent read model 和稳定 source 去重 |
| 预计回款掩盖应付 | 组合金额过于乐观 | 预计流入单列，默认不抵扣准确/确认支出 |
| 原 PDF 默认不保存 | 跨设备无法完整预览 | 保存页级证据和 hash；诚实提示原件不可用；附件能力另行立项 |
| 新数据未进 Archive | 恢复后来源链断裂 | 每期 Archive 往返和实体关系对账作为发布硬门 |
| 功能扩张偏离定位 | 变成建议/预算工具 | 文案与范围审查；不可越过边界写入每期验收 |

## 7. 编码前需要冻结的决策

以下不是要求用户现在回答的问题，而是相应 Phase 开工前必须记录到正式契约的决策门：

1. **原 PDF 保留策略**：默认不长期保存；是否需要可选加密保存应另行评估。
2. **首批真实银行 profile**：根据用户实际账单选择 2–3 类，不以网上样本臆测格式。
3. **多模态 Provider 边界**：何时文本/OCR 判定不足，哪些页允许上传图像。
4. **部分确认语义**：允许分批确认，但每次所选行必须原子成功；批次完成需全部 resolution。
5. **未对平确认策略**：推荐允许用户在显著警示后确认已复核行，同时批次保留 `validation_failed` 事实，绝不标记“已对平”。
6. **商户实体命名**：采用 `merchant` 还是更通用的 `counterparty`，以及退款/转账对手方边界。
7. **组合余额正式名称**：推荐“扣除已确认应付后余额”，避免“可支配”“安全可花”。
8. **分期计划是否进入组合金额**：推荐仅在成为 exact due 后进入；此前只以 scheduled 单列。
9. **v1.5 原生入口范围**：Widgets/Spotlight 如影响核心质量，允许顺延到 v1.5.x。

## 8. 明确留在 v1.5 之后的事项

以下项目不进入本 backlog，也不应在 v1.4/v1.5 施工中顺手扩展：

- 预算、信封预算、分类限额。
- 消费建议、财务健康分、异常消费评价。
- “安全可花”或基于模型的可消费金额。
- 历史趋势外推、未来消费预测。
- 情景模拟和决策辅助。
- 银行/Open Banking 自动连接器和网页爬虫。
- AI 聊天、自动财务总结建议。
- 投资、证券、基金、加密资产和多币种。
- 多人、家庭账本和权限系统。
- 通用附件中心、完整插件市场和第三方写入生态。

后续方向只根据真实使用中出现的“事实没有被记录”或“事实不容易看清”继续演进，不以功能数量作为目标。

## 9. 最终 Definition of Done

### v1.4

用户能选择真实银行 PDF，知道哪些内容将发送给哪个 LLM，看到每一行的原始证据、识别结果、校验状态和重复匹配；在最终确认前，账本没有任何变化。确认后，每笔新增流水都遵循手工记账相同的领域规则，并能从账本追溯回账单批次。失败、重试、重复文件和跨设备冲突都不会重复记账。

### v1.5

用户打开 Fiscal 后，可以准确看到过去花了什么、现在有多少现金和负债、未来已经明确要支付或收到什么；“扣除已确认应付后余额”具有公开公式、确定性分层和完整下钻。系统不提供预算、评价、建议或预测，所有数字仍是可验证的事实陈述。
